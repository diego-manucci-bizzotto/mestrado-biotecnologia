4) SCANNING AND STATISTICAL PIPELINE (CURRENT IMPLEMENTATION)
======================================================================

Core file:
- backend/app/services/scanner.py

Pipeline:
1. Parse FASTA records.
2. Estimate 0-order background frequencies from FASTA (A/C/G/T).
3. Build motif model:
   - For user IUPAC, derive PWM (with pseudocount in iupac->pwm flow).
4. Scan both strands (+ and reverse-complement).
5. For each window:
   - Compute PWM log-odds score.
   - Convert score to p-value using score distribution.
6. Keep PWM hit if p_value <= p_value_cutoff.
7. Compute BH q-values for collected hit p-values.
8. Build summary metrics.

Score distribution logic:
- backend/app/services/pwm.py
- If motif length <= 10:
  - Enumerate all 4^L kmers (exact distribution)
- If motif length > 10:
  - Monte Carlo sampled distribution (sample_count=100000, fixed RNG seed)

Per-hit fields:
- window_p_value
- gene_p_value (gene-level presence approximation from window probability)
- q_value (BH corrected over collected hits)

======================================================================
5) ENRICHMENT METRICS (CURRENT IMPLEMENTATION)
======================================================================

Global expected hits:
- expected_hits = total_windows * probability_for_iupac(motif, background)

Global enrichment p-value:
- poisson_survival(observed_hits, expected_hits)
- Interpreted as right-tail probability under Poisson null.

Global enrichment q-value:
- BH over a single p-value list [enrichment_p_value]
- Practical consequence: enrichment_q_value == enrichment_p_value in current code.

======================================================================
6) CURRENT SCIENTIFIC LIMITATIONS TO TRACK
======================================================================

1) Enrichment model mismatch for PWM mode:
- Hit selection is based on PWM threshold,
  but expected_hits for enrichment is based on IUPAC probability.

2) q-value family definition:
- BH is applied to collected hits, not explicitly to all tested windows.

3) Background model:
- 0-order background only (A/C/G/T frequencies),
  no higher-order Markov effects.

4) Short motifs behavior:
- Short/degenerate motifs can produce many hits under null,
  often leading to weak global enrichment signal (p near 1).

9) CHANGE LOG ENTRY - 2026-05-27
======================================================================

Change ID:
- STATS-POISSON-STABILITY-001

Date:
- 2026-05-27

Files changed:
- backend/app/services/statistics.py
- backend/tests/test_statistics.py
- docs/pwm_only_cutover_enrichment_changes.txt

What changed:
- Replaced direct Poisson right-tail accumulation with regularized
  incomplete-gamma evaluation (series + continued fraction split).

Why changed:
- Direct exp(-lambda)-based accumulation is numerically unstable for large
  lambda and can produce underflow artifacts in enrichment p-values.

Expected scientific impact:
- Enrichment p-values remain mathematically equivalent but numerically stable,
  especially when total windows and observed hits are large.

Validation done:
- Backend tests executed with new regression cases.
- Result: 8 passed.

Date:

Files changed:
- backend/app/main.py
- backend/README.md

- backend/tests/conftest.py

What changed:
- `main.py` now supports both run modes:
  - `uvicorn app.main:app` from `backend/` (recommended)
  - `uvicorn main:app` from `backend/app/` (fallback)

Why changed:
- Relative imports fail when a module is loaded as top-level (`main`) without

  "attempted relative import with no known parent package".

Expected impact:
- Eliminates startup crashes caused by cwd/entrypoint mismatch.

Validation done:
- Import checks passed in both modes.
- Backend tests passed (8/8).

Reference:
- Python documentation: relative imports depend on package context and the main
  module is a special case in the import system.
  https://docs.python.org/3.10/reference/import.html
  https://docs.python.org/3/tutorial/modules.html

- backend/tests/test_scanner.py
- backend/tests/test_api_contract.py

What changed:
- Added directional and effect-size summary fields:
  - `depletion_p_value = P(X <= observed_hits)`
  - `two_sided_p_value = min(1, 2*min(P(X >= observed_hits), P(X <= observed_hits)))`
  - `fold_change = observed_hits / expected_hits`
- Kept existing enrichment fields unchanged:
  - `enrichment_p_value`, `enrichment_q_value`
- Frontend summary cards now display:
  - Depletion p-value
  - Two-sided p-value
  - Fold-change (Obs/Exp)

Why changed:
- A one-sided enrichment p-value can be ~1 when observed < expected; this is
  statistically correct but hides depleção signal if shown alone.
- Directional + two-sided outputs make interpretation explicit and auditable.

Expected scientific impact:
- Prevents false interpretation of `p=1` as "pipeline bug".
- Distinguishes "no enrichment" from "strong depletion".
